# Terraform Architecture: Providers and Enterprise Deployment Patterns

This document covers two topic areas that share a common thread — how Terraform is configured to talk to the *right* cloud environment, safely, at organizational scale: **provider engineering** (aliases, auth, versioning, air-gapped operation) and **enterprise architecture** (multi-account, multi-region, multi-environment, layered deployment). It backs [`interview-questions/04-providers.md`](../interview-questions/04-providers.md) and [`interview-questions/05-aws-architecture.md`](../interview-questions/05-aws-architecture.md), and is exercised in [Lab 5](../labs/lab-05-multi-environment/), [Lab 8](../labs/lab-08-aws-networking/), and [Lab 15](../labs/lab-15-enterprise-capstone/).

## Part A — Provider Engineering

### 1. Provider configuration, aliases, and inheritance

A single Terraform configuration frequently needs to talk to more than one AWS account or region simultaneously — a shared-services account, a workload account, and a DNS account, for example. This is done with **provider aliases**:

```hcl
provider "aws" {
  region = "us-east-1"
}

provider "aws" {
  alias  = "dns_account"
  region = "us-east-1"
  assume_role {
    role_arn = "arn:aws:iam::111111111111:role/terraform-dns-admin"
  }
}

resource "aws_route53_record" "app" {
  provider = aws.dns_account
  # ...
}
```

**Module provider inheritance:** by default, a child module inherits the *default* (unaliased) provider configuration of its caller automatically — you do not need to pass it explicitly. Aliased providers must be **explicitly passed** into a module via the module's `providers` block if that module needs to operate against a non-default provider configuration:

```hcl
module "dns_records" {
  source = "./modules/dns"
  providers = {
    aws = aws.dns_account
  }
}
```

A module that itself declares `provider` blocks (rather than only accepting provider configuration from its caller) cannot be safely reused across multiple accounts/regions by its consumers — this is why reusable modules should generally **not** hard-configure providers internally, and should rely entirely on inherited or explicitly passed provider configuration.

### 2. Multi-account, multi-region assume-role architecture

The standard enterprise pattern: a **central identity/CI account** holds the OIDC-federated role or long-lived automation identity, which **assumes a role into each target account** with only the permissions needed in that account. This keeps blast radius contained (a compromised CI credential is limited to the roles it was explicitly granted assume permission for) and keeps IAM policy management centralized and auditable.

```hcl
provider "aws" {
  alias  = "workload_prod"
  region = var.aws_region
  assume_role {
    role_arn     = "arn:aws:iam::${var.workload_account_id}:role/terraform-execution"
    session_name = "terraform-${var.environment}"
  }
}
```

For multi-region within the same account, you declare one aliased provider per region and pass the correct one to region-specific resources/modules — there is no "global" provider that operates across regions implicitly; every AWS resource is created via a specific regional (or global-endpoint, e.g., IAM/Route53) provider configuration.

### 3. Provider version constraints and the dependency lock file

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.40"
    }
  }
}
```

`required_providers` constrains the *allowed range*; `.terraform.lock.hcl` (generated by `init`, and **must be committed to version control**) pins the *exact resolved version and checksums* actually installed, so every engineer and every CI run gets byte-identical provider binaries until someone deliberately runs `terraform init -upgrade`. This is what prevents "it worked on my machine" and prevents an unreviewed provider version drift from silently changing plan behavior between two runs of the same commit.

**Provider upgrade risk:** a minor provider version bump can change: which attributes are `ForceNew` (triggering unexpected replacements — see [`terraform-internals.md`](terraform-internals.md#9-provider-rpc-communication)), default value handling (e.g., a provider starts treating an omitted optional field differently), or resource schema fields entirely (a field renamed/removed/added). Treat `terraform init -upgrade` as a change that gets its own reviewed PR with a `terraform plan` diff attached — never bundle a provider upgrade silently inside an unrelated feature change, and always run the upgrade's resulting plan against a non-production environment before touching production state.

### 4. Default tags

```hcl
provider "aws" {
  default_tags {
    tags = {
      ManagedBy   = "terraform"
      Environment = var.environment
      Repository  = "platform-infrastructure"
    }
  }
}
```

`default_tags` applies organization-wide tagging without repeating it on every resource — but note it merges with (and can be overridden by) resource-level `tags`, and some resource types/attributes are exempt from provider-level default tag propagation depending on provider version; verify against current `hashicorp/aws` provider documentation rather than assuming universal coverage.

### 5. Authentication — avoiding credentials in code

**Never** hard-code `access_key`/`secret_key` in provider blocks or `.tfvars`. The modern, recommended pattern end to end:
- **Local development**: named AWS CLI profiles backed by SSO (`aws sso login`) or short-lived assumed-role credentials — never long-lived IAM user access keys checked into any file.
- **CI/CD**: **OIDC federation** — the CI platform (GitHub Actions, GitLab CI) presents a signed OIDC token to AWS STS, which exchanges it for short-lived credentials scoped to a specific IAM role, with trust policy conditions restricting *which* repository/branch/environment can assume it. No stored AWS secret exists anywhere in CI configuration. See [`cicd.md`](cicd.md) and [Lab 12](../labs/lab-12-cicd-pipeline/) for the full trust-policy and workflow configuration.
- **Terraform Cloud/Enterprise**: dynamic provider credentials via workload identity (TFC's own OIDC-based mechanism), which extends the same "no stored long-lived secret" model to the Terraform Cloud execution environment itself.

### 6. Provider installation, mirrors, and air-gapped environments

`terraform init` downloads providers from the public registry by default. In an air-gapped or high-security environment, use:
- A **filesystem or network mirror** (`terraform { provider_installation { filesystem_mirror { ... } } }` in the CLI config, or a `network_mirror` pointing at an internal Artifactory/Nexus-style mirror) to serve pre-vetted provider binaries without any egress to the public internet.
- The dependency lock file's recorded checksums are validated against the mirror's binaries exactly as they would be against the public registry — the trust model doesn't weaken just because the source moved internal.

**Supply-chain consideration:** treat provider and module sources the same way you'd treat any third-party dependency — pin versions, verify checksums (the lock file does this automatically), and for anything pulling community (non-HashiCorp, non-verified-partner) providers/modules into production paths, have an internal review/allowlist process. A malicious or compromised provider binary has the same blast radius as a compromised CI credential, since it runs with whatever credentials your Terraform execution environment has.

## Part B — Enterprise Architecture

### 7. Layered deployment architecture

The pattern used throughout this repository (fully realized in [Lab 15](../labs/lab-15-enterprise-capstone/)):

```text
Bootstrap layer      — state backend (S3/DynamoDB or equivalent), CI/CD OIDC identity/roles
    └── deployed once per account/org, extremely rarely changed, own state

Foundation layer      — accounts/OUs, baseline IAM, core VPC/networking, security controls (GuardDuty, Config, SCPs)
    └── owned by a platform/security team, changes infrequently, own state

Platform layer        — EKS or shared compute, shared load balancing, observability stack, secrets integration
    └── owned by a platform team, changes moderately, own state per environment

Application layer     — application-specific infrastructure, databases, application IAM roles
    └── owned by application teams, changes frequently, own state per application per environment
```

**Why each layer needs its own state and deployment lifecycle:**
- **Blast radius**: an application team's daily changes should be structurally incapable of touching foundation-layer networking or IAM, because they don't even have write access to that state or those credentials — not because of code review discipline alone.
- **Change frequency mismatch**: foundational networking might change quarterly; application infrastructure changes daily. Sharing state forces every application change to wait behind (or risk colliding with) foundational locks, and vice versa.
- **Ownership clarity**: state boundaries should mirror team ownership boundaries — when they diverge (a platform team's resources living in an application team's state), approvals and accountability become ambiguous.
- **Independent rollback**: a bad application-layer apply must be revertable without any risk to foundation/platform layers, and vice versa.

Cross-layer references use the parameter-store/data-source pattern from [`state-management.md`](state-management.md#10-cross-state-dependencies), not shared state or `terraform_remote_state` across ownership boundaries.

### 8. Multi-account strategies: landing zones and account vending

At real enterprise scale (dozens to hundreds of AWS accounts), manually creating and configuring each account doesn't scale. **Landing zone** patterns (AWS Control Tower, or a custom-built equivalent) combine:
- **Account vending**: a standardized, automated (often Terraform-driven, sometimes via Service Catalog or Control Tower Account Factory) process to create a new account pre-configured with baseline guardrails (SCPs, logging, security tooling) already applied — so no account is ever provisioned "bare."
- **Delegated ownership**: application teams get accounts (or account-scoped roles) they can operate within freely, constrained by organization-wide SCPs they cannot override — this is what lets a large organization avoid a single central team being the bottleneck for every infrastructure change, while still enforcing non-negotiable guardrails (no public S3, mandatory encryption, approved regions only).

**100-account, multi-region deployment design** (a canonical senior question — [`interview-questions/05-aws-architecture.md`](../interview-questions/05-aws-architecture.md)): the answer combines provider aliasing/assume-role (§2) for account+region targeting, per-account-per-environment state separation (§7), a pipeline architecture that parameterizes account/region as inputs to a shared, tested module set rather than hand-writing per-account configuration (see [`cicd.md`](cicd.md) for matrix-based pipeline execution), and centralized policy enforcement (SCPs plus [Lab 13](../labs/lab-13-policy-as-code/) policy-as-code checks in the pipeline) so guardrails don't depend on every team remembering them.

### 9. Repository architecture: monorepo vs. repository-per-environment

- **Monorepo** (one repository, environments as directories/workspaces): simpler cross-environment refactors (one PR touches dev/staging/prod code together), easier to keep modules in sync, but requires strong directory/path-based CI triggering and access control discipline to prevent an application-team PR from having *write access* (even if not applied) to production configuration files.
- **Repository-per-environment or repository-per-team**: stronger natural access-control boundary (GitHub/GitLab repo permissions directly gate who can even propose a change to production config), but cross-cutting module upgrades now require coordinated PRs across many repos — this is exactly the versioning discipline problem from [`module-design.md`](module-design.md#5-module-versioning-and-semantic-versioning).

Neither is universally correct; the decision should follow the same ownership-boundary logic as state separation (§7) — and **workspaces alone are not a substitute for either pattern** for production isolation (see §10).

### 10. Why CLI workspaces are not sufficient for production isolation

`terraform workspace new production` creates a separate state *within the same backend configuration and, critically, the same configuration code*. This means: the same variable defaults, the same provider configuration approach, and — most importantly — **a single `terraform apply` invocation targeting the wrong workspace is a one-flag mistake** (`-var-file` or workspace-selection error) away from applying production-shaped intent against a workspace you didn't mean to touch, or vice versa. Workspaces are appropriate for genuinely ephemeral, structurally-identical environments (e.g., a developer's personal sandbox, PR-preview environments) — not for the dev/staging/production boundary, which should have separate root module invocations (distinct backend configuration blocks, ideally distinct state bucket paths and distinct credentials/roles) so that "which environment am I about to apply to" is determined by *which directory and which credentials you're in*, not by a mutable CLI-selected pointer. [Lab 5](../labs/lab-05-multi-environment/) implements this explicitly and demonstrates the isolation workspaces alone can't provide.

### 11. Immutable infrastructure and blue-green patterns

**Immutable infrastructure**: instead of updating a running resource in place (mutable), replace it wholesale with a new instance built from a new image/version, then cut over — reduces configuration drift (nothing is ever hand-patched in place) and makes rollback trivial (redeploy the previous known-good artifact). Terraform's `create_before_destroy` (see [`terraform-internals.md`](terraform-internals.md#5-depends_on-lifecycle-and-the-meta-arguments)) is the core primitive enabling this at the resource level.

**Blue-green infrastructure**: maintain two full environments (blue = current live, green = new candidate), validate green independently, then shift traffic (DNS weighting, load balancer target group swap, or similar) — Terraform typically manages *both* environments' infrastructure declaratively, with the traffic-shift itself often being a narrowly-scoped, fast, and easily-reversible final step (e.g., updating a Route 53 weighted record or an ALB listener rule) rather than a full infrastructure replacement, precisely so rollback is a traffic-shift, not a redeploy.

### 12. Disaster recovery architecture

Covered fully in [`ha-dr.md`](ha-dr.md); the architecture-level summary: DR strategy (backup/restore, pilot light, warm standby, multi-site active/active) determines your **Terraform deployment topology** — whether you maintain one region's configuration with a documented "deploy this same config to the DR region" runbook (cheaper, slower recovery), or continuously apply the same configuration to two regions simultaneously via a pipeline matrix (more expensive, near-zero recovery time). Either way, the configuration for the DR region should be **the same modules, parameterized by region/account** — never a hand-maintained, drifted-over-time separate copy, which defeats the purpose of DR by the time you actually need it.

## Common weak answer vs. senior answer

| Scenario | Weak answer | Senior answer |
|---|---|---|
| 100 accounts, multiple regions | "Use a `for_each` over accounts" | Combine provider aliasing/assume-role per account+region, per-account-per-env state separation, pipeline matrices parameterizing account/region against shared tested modules, and centralized SCP + policy-as-code guardrails |
| Isolating prod from dev | "Use `terraform workspace select production`" | Workspaces share configuration code and are one flag away from cross-environment mistakes; production isolation needs separate root module invocations with separate backends/credentials |
| Provider upgrade before a release | "Run `init -upgrade` and apply" | Treat it as its own reviewed change with a full plan diff, tested in non-prod first, because minor bumps can change ForceNew behavior and defaults |
| Reducing blast radius | "Split the Terraform files into more modules" | Child modules don't create state boundaries; blast-radius reduction requires separate root modules/state along ownership and change-frequency lines |
