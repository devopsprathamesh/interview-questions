# Cheat Sheet: Common Production Failure Patterns

| Symptom | Root cause | Fix | Reference |
|---|---|---|---|
| Task reports `changed: true` every single run | `command`/`shell` with no idempotency guard | Use a purpose-built module, or add `creates:`/`changed_when` | [Q1](../interview-questions/01-ansible-core.md#question-1-the-playbook-that-broke-on-the-second-run) |
| Handler never fires despite being notified | An earlier task in the same play failed before reaching the flush point | Add explicit `meta: flush_handlers` if timing-sensitive | [Q2](../interview-questions/01-ansible-core.md#question-2-the-restart-that-never-happened) |
| Loop silently processes half the expected items | List variable fully replaced (not merged) by a higher-precedence source | Debug-print the resolved variable right before the loop | [Q3](../interview-questions/01-ansible-core.md#question-3-the-loop-that-quietly-skipped-half-its-work) |
| `when` condition always evaluates true/false unexpectedly | Typo'd variable name; undefined comparison silently resolves to `false`, not an error | Add an `assert` verifying the variable is defined and valid | [Q5](../interview-questions/01-ansible-core.md#question-5-the-conditional-that-always-evaluated-true), [Q92](../interview-questions/10-troubleshooting.md#question-92-the-playbook-that-succeeded-by-doing-nothing) |
| `rescue` block completes, play reports success, but something serious happened | Rescue catches *any* failure, not just the expected one | Inspect `ansible_failed_result` inside rescue; re-raise anything unexpected | [Q6](../interview-questions/01-ansible-core.md#question-6-the-block-that-recovered-silently), [Q93](../interview-questions/10-troubleshooting.md#question-93-the-rescue-block-that-rescued-the-wrong-thing) |
| `--check --diff` shows no changes, real run shows several | `command`/`shell` tasks are check-mode-blind | Never trust `--check` alone for playbooks using `command`/`shell` heavily | [Q7](../interview-questions/01-ansible-core.md#question-7-the-check-mode-run-that-lied) |
| Fleet-wide run takes 40 minutes for a trivial change | `forks` left at low default (5) against a large inventory | Increase `forks`, validated against control-node capacity | [Q8](../interview-questions/01-ansible-core.md#question-8-the-fleet-that-took-forty-minutes-to-patch-one-line) |
| Role behaves differently than documented, override doesn't work | Role `vars/main.yml` beats `defaults/main.yml` in precedence | Move the overridable value to `defaults` | [Q12](../interview-questions/02-inventory-variables.md#question-12-the-role-that-couldnt-be-overridden) |
| Zero hosts matched, no error, playbook "succeeds" | Tag/filter typo in dynamic inventory pattern | `ansible-inventory --graph` to confirm actual resolution; add a zero-host `assert` guard | [Q11](../interview-questions/02-inventory-variables.md#question-11-the-play-that-matched-zero-hosts) |
| `.retry` file misses some genuinely-failed hosts | `.retry` only reliably tracks certain failure categories | Derive the complete non-succeeded host list from the full `PLAY RECAP`, not `.retry` alone | [Q87](../interview-questions/10-troubleshooting.md#question-87-the-retry-file-that-told-half-the-story) |
| Pod-restart-equivalent alert fires hundreds of times during a routine rollout | Alerting on every individual event instead of business-impact symptoms | Alert on elevated error rate/latency, not per-restart | (Category 9 pattern, cross-referenced from the companion EKS repository) |
| Intermittent (~2%) failure, always resolves on retry, never diagnosed | Evidence discarded by immediately retrying instead of capturing it first | Capture full `-vvv` output *before* retrying, across several occurrences | [Q98](../interview-questions/10-troubleshooting.md#question-98-the-incident-nobody-could-reproduce-because-nobody-kept-the-evidence) |
| Vault-encrypted value visible in plaintext in terminal output | `--check --diff` shows the rendered, decrypted value | Add `no_log: true` to the specific templating task | [Q64](../interview-questions/07-security-vault.md#question-64-the-vault-encrypted-variable-that-was-still-visible-in-plan-output) |
